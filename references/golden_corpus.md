# Золотой корпус — регрессионная батарея детектора

Тестовая батарея для Детектора 2.0 (§25–28 v2.0 + white-list 25.27). Все фрагменты синтетические (написаны для корпуса), чтобы не зависеть от чужих прав. Правило: любое изменение §25–§28 прогоняется по корпусу ЦЕЛИКОМ до принятия.

[источник: Notion, 2026-07-11]

---

## Протокол регрессии

1. Прогнать все кейсы через текущую версию детектора и сравнить с колонкой «Ожидание».
2. Регресс = любой кейс сменил вердикт. Правило откатывается или уточняется.
3. Каждое новое правило детекции обязано прийти с парой кейсов: один ловится (true positive), один похожий, но живой (false-positive ловушка).
4. Метрики: FP (живое помечено как слоп) хуже, чем FN (слоп просочил). Цель: FP = 0, FN ≤ 1 на корпус.

```

- Ожидание: truncation НЕ флагуется (формульная секция + след события в тексте). До 25.27 был бы ложный hard-fail — контроль регресса.

### G-11 · припев-формула с накоплением (пара к G-06)

### G-15 · marker_word (true positive, пара к G-16, issue #4)
```

Тот же кейс страхует tech_metaphor: «серверная» без эмоционального существительного рядом — грунт мира героя, а не технометафора.

### G-19 · not_x_but_y (true positive, пара к G-20, issue #4)
```
это было не просто расставание — это было предательство,

```
- Ожидание: not_x_but_y (1.5) — точная формула §16.3 «Это было не просто X — это было Y»: пустой усилитель «не просто» + эхо копулы «это было» через тире → подозрение.

### G-20 · not_x_but_y false-positive ловушка («не просто» без эха копулы)
```
не просто устал — хочу уже домой,

```
- Ожидание: 0 флагов not_x_but_y. «не просто … —» само по себе не формула: после тире нет повтора «это было/это был», а есть живое продолжение с действием. Реализован только узкий паттерн; две более широкие альтернативы из §30.2 («это не X — это Y» и голое «не X, а Y») сознательно не включены — см. комментарий над NOT_X_BUT_Y_RE в `scripts/lint_patterns.py`.

- Ожидание: position_explanation ×3 (1.5) — герой объясняет свою моральную позицию вместо действия. Важно: denial_gap тут НЕ срабатывает («сужу» не в закрытом списке глаголов отрицания) — два флага не должны сливаться.

### G-22 · position_explanation false-positive ловушка (конкретная память и чужой суд)
```
я помню номер дома и запах хлорки,

```
- Ожидание: 0 флагов position_explanation. «я помню» с конкретным объектом — не штамп «я помню всё»; «судить» с внешним субъектом — не штамп «не мне судить». Контроль границы: проверка держится только на закрытом списке фраз, а не на ключевых словах.

### G-23 · truncation (true positive, пара к G-24, issue #4)
```

потом было утро. …дальше — позже.
```
- Ожидание: truncation ×4 (2.0) → hard-fail. Синтетический worst-case: в одном кейсе собраны все четыре канонических маркера §25.13, чтобы каждая альтернатива регекса была покрыта корпусом, а не только комментарием в коде.

### G-24 · truncation false-positive ловушка (сцена доведена до конца)
```

```
- Ожидание: 0 флагов truncation. «потом стало» ≠ «потом было», «рассказал всё» ≠ «я помню всё». Главное: проверка принципиально НЕ судит об умолчании как таковом — за это отвечает white-list 25.27 (G-01, G-10), иначе живая недосказанность получила бы hard-fail.

### G-25 · tech_metaphor (true positive, пара к G-26, issue #4)
```
слёзы в формате WAV, любовь в кэше,
память в логах, я перезагружаю чувства до утра.
сердце в архиве, душа на сервере, файл одиночества открыт.
код души лежит в корзине.
```
- Ожидание: tech_metaphor ×8 (2.0) → hard-fail. Синтетический worst-case: в одном кейсе собраны все восемь альтернатив §25.2 / §30.2, чтобы каждая была покрыта корпусом, а не только комментарием в коде. Живой пример того же флага — G-05.

### G-26 · tech_metaphor false-positive ловушка (тех-лексика как грунт)
```
память держит весь наш диалог до последнего слова
сердце заходится, я сижу тут третий час и правлю чужой код
```
- Ожидание: 0 флагов. Кейс целенаправленно проверяет два сужения, без которых буквальный регекс спеки даёт hard-fail на живом тексте: строка 1 — «лог» внутри «диалога» (тех-токен обязан начинать слово), строка 2 — «сердце» и «код» в одной строке, но на расстоянии больше 40 символов, то есть это две разные клаузы, а не одна метафора. Сравни с G-16: технический сеттинг сам по себе не есть технометафора.

### G-27 · hypophora (true positive, пара к G-28, issue #4)
```
почему я всё ещё набираю твой номер?
потому что помню его лучше, чем свой.
```
- Ожидание: hypophora (1.5) → подозрение. Вопросительная строка + немедленный ответ через закрытый коннектив «потому что» на следующей физической строке (без пропуска через пустую строку/смену строфы).

### G-28 · hypophora false-positive ловушка (вопрос без маркированного ответа)
```
почему ты не спишь, ведь уже поздно?
на кухне свет горит, я жду тебя с работы.
```
- Ожидание: 0 флагов hypophora. Строка после вопроса не начинается ни с одного из закрытых коннективов («потому что», «оттого что», «затем что») — обычное сюжетное продолжение сцены не считается формульным ответом. Именно эта граница отличает механическую проверку от семантической версии правила («любая строка после вопроса — это ответ»), которая раньше держала hypophora в списке отложенных флагов.

### G-29 · verb_rhyme + banal_rhyme (true positive, пара к G-30, issue #4)

### G-30 · verb/banal_rhyme false-positive ловушка (банальные слова вне рифменной позиции)
```

- Ожидание: 0 флагов. «ночь» (начало строки 1) и «прочь» (середина строки 3) присутствуют в тексте, но ни одно не стоит на конце строки — банальная пара засчитывается только в рифменной позиции. «я не сплю» — единственное отрицание, легально (максимум 1 на текст, см. denial_gap). Именно позиционное требование отличает механическую проверку от наивного поиска слов из списка по всему тексту, который ловил бы живые тексты.
